# Классификация v2: согласованное применение и откат

Это инструкция для отдельного разрешённого операторского окна. PR ничего не
подключает, не разворачивает и не выполняет DDL. Не запускать `server.ts` для
проверки. Использовать утверждённую БД и учётную запись оператора; не выводить URI,
финансовые документы, токены или fingerprints в журналы.

## Поведение

- Новый подтверждённый intent сохраняет `financial-classification-v2`.
  `ordinary_expense/emergency` разрешён; `loan_issuance` отвергается до записи.
- Документы v1 читаются по правилам v1, включая исторический `loan_issuance`.
  Чтение и повтор последнего идентичного запроса не меняют документ или ревизию.
  Replay сверяет хеш с исходной taxonomy. Новый явный intent с актуальной CAS
  ревизией заменяет текущее решение документом v2. Массового обновления нет.
- HTTP-маршруты, `classification-decision-v1`, `classification-read-v1` и формат
  команд остаются прежними. Клиент не выбирает taxonomy. Исходные финансовые
  операции, их категории, source fingerprint и расчёты не меняются.
- Старые review proofs для оставшихся допустимых ролей проверяются с прежними
  привязками/сроками; новые proofs содержат v2. Новая команда с `loan_issuance`
  не принимается ни через один путь записи.

## Перед применением

1. Зафиксировать SHA старого и нового backend, конфигурацию флагов и имя БД.
   Подтвердить readiness старой сборки и сохранить точные текущие validator и
   индекс; неожиданное состояние не исправлять в этом переходе.
   Отключить запись классификаций на **всех** экземплярах:
   `CLASSIFICATION_C_WRITE_ENABLED`, `CLASSIFICATION_WRITE_ENABLED`,
   `CLASSIFICATION_REVIEW_ENABLED`, `CLASSIFICATION_RECONCILE_ENABLED` — не `1`.
   Исключить внутренние writer-вызовы, дождаться завершения запросов. Старые
   процессы/preparation handles не должны пережить переключение. Снять блокировку
   только после проверок ниже; исключить параллельные DDL и восстановление.
2. Сделать согласованную резервную копию БД и каталога. Для standalone на время
   копии приостановить **все** записи приложения/заданий, включая финансовые.
   Использовать действующую проверенную процедуру, например `mongodump` с явно
   заданными оператором URI/БД и защищённым archive; проверить восстановление в
   отдельной среде. Сохранить `getCollectionInfos` (validator, level/action,
   collation) и `getIndexes()` для `operation_classifications` в EJSON, отдельно
   от журналов. Зафиксировать количество документов, распределение v1/v2 и
   контрольные данные копии. Без проверенной копии не продолжать.
3. Собрать выбранный backend (`npm ci`, `npm run typecheck`, `npm run build`).
   Экспортировать **именно его** manifest в защищённый файл; импорт manifest не
   подключается к БД:

   ```sh
   node -e 'process.stdout.write(JSON.stringify(require("./dist/persistence/classificationManifest.js").CLASSIFICATION_MANIFEST.options))' > /secure/classification-v2-options.json
   ```

## Применение оператором

Старый backend требует точный старый validator, новый — точный переходный.
Нельзя расширить validator и оставить старые процессы обслуживать классификацию:
их readiness станет false. На время переключения закрыть доступ к классификации
или остановить соответствующие процессы; обычные финансовые данные не менять.

В явно выбранной БД через `mongosh` вручную выполнить следующий фрагмент. Путь
должен указывать на проверенный файл из новой сборки. Сначала выполняются только
проверки; неизвестные версии/повреждённые документы требуют остановки, а не repair.

```js
const name = 'operation_classifications';
const desired = JSON.parse(require('fs').readFileSync('/secure/classification-v2-options.json', 'utf8'));
const info = db.getCollectionInfos({name});
if (info.length !== 1 || info[0].type !== 'collection') throw new Error('STOP: namespace mismatch');
if (db.getCollection(name).find({$nor: [desired.validator]}).limit(1).hasNext())
  throw new Error('STOP: incompatible classification; do not rewrite documents');
const result = db.runCommand({collMod: name, validator: desired.validator,
  validationLevel: desired.validationLevel, validationAction: desired.validationAction});
if (result.ok !== 1) throw new Error('STOP: validator not applied');
```

`collMod` меняет только проверку документов. Не выполнять `updateMany`, backfill,
переименование категорий, пересоздание коллекции или индексов. `expenses` и
`incomes` не затрагиваются. Индекс `ux_owner_dataset_operation` остаётся прежним.

Установить новый backend с выключенными флагами. Через существующий
`classificationReadiness(db)` из **этой сборки** проверить `true`: это read-only
проверка точного validator, strict/error, collation и полного unique index.
Не обходить readiness, не заменять сравнение приблизительным и не включать
`autoIndex`/`autoCreate`. При `false` оставить запись отключённой.

Сверить каталог с manifest, количество/версии документов с копией, отсутствие
несовместимых документов запросом выше. Проверить чтение ранее существовавших v1
через обычный авторизованный API: assignment/revision должны сохраниться.
Восстановить только прежние разрешённые read/write-флаги по решению оператора.
Первую запись v2 проверять на операции, которую пользователь действительно
классифицирует: явный выбор группы, один PUT, чтение подтверждённого результата;
серверный документ должен иметь v2 и следующую ревизию. Не создавать финансовые
операции ради проверки и не пересылать автоматически команды с неизвестным исходом.

## Откат

Сначала выключить и осушить запись на всех экземплярах. Если v2 ещё **не записана**,
можно вернуть сохранённые прежние validator/level/action через ручной `collMod`,
старый backend и его конфигурацию. Проверить readiness старой сборки и чтение v1.
Не пересоздавать индекс и не трогать документы.

Если есть хотя бы один документ v2, безопасный откат — оставить совместимые
reader/переходный validator, отключив новые записи. Старый backend не умеет читать
v2 и не пройдёт readiness с переходным validator. Не понижать taxonomy и не
возвращать старую БД поверх новых финансовых операций. Полный возврат к старой
сборке потребует отдельного решения о восстановлении классификаций и возможной
потере подтверждённых изменений после копии; автоматически этого не делать.
